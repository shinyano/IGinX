# 自适应 Python UDF 调度池动态扩缩容实验分析

## 实验目的与评价思路

本节围绕 IGinX 自适应 Python UDF 调度池在自由线程 Python 运行环境下的动态行为展开实验分析。实验目标是验证调度器在时间变化负载下是否能够按照设计预期完成扩容、缩容和再次扩容，并考察线程池规模变化是否能够与队列长度、EWMA 指标、吞吐和查询延迟形成一致的解释链条。根据实验设计文档中的研究问题，本文重点关注四个方面：高峰阶段是否能够在队列积压出现后触发扩容，负载回落后是否能够逐步缩容，经历一次完整扩缩容后是否能够在二次高峰中继续响应，以及运行指标之间是否具有可解释的一致性。

为保证观察结果具有时序可解释性，实验同时采集客户端秒级时间序列和服务端调度器结构化日志。客户端侧记录每秒完成请求数、`P50` 延迟和 `P95` 延迟，服务端侧记录 `poolSize`、`activeThreads`、`queueLength`、`cpuUsage` 及其 EWMA 平滑值，并将每个秒级样本与不晚于该采样时刻的最近一条调度快照对齐。由此可以在同一时间轴上观察外部性能结果与内部调度状态之间的对应关系，这也是判断自适应策略是否按设计工作的主要依据。

## 实验环境与参数设置

实验运行在自由线程 Python 环境下，客户端时间序列记录显示本轮实验使用的 Python 版本为 `3.13.12`，且 `gilEnabled=0`。工作负载采用 `DataFrame -> NumPy` 的向量化计算路径，单次实验固定数据规模为 `rows=10000`、`cols=10`、`loops=20`。调度池参数保持固定，其中初始线程数为 `4`，最小线程数为 `4`，最大线程数为 `96`，调度周期为 `2000 ms`，冷却时间为 `5000 ms`，队列扩容阈值为 `5`，缩容阈值为 `1`，CPU 高水位阈值为 `0.85`，CPU 低水位阈值为 `0.30`。这些参数与实验文档中的正式实验配置一致，因此不同阶段的行为可以直接与设计预期对应。

动态负载时间线采用五阶段阶梯式设计，总时长为 `210 s`。`Phase 1` 为 `0-30 s` 的预热阶段，并发数为 `4`；`Phase 2` 为 `30-90 s` 的主高峰阶段，并发数提升至 `32`；`Phase 3` 为 `90-130 s` 的回落阶段，并发数降回 `4`；`Phase 4` 为 `130-160 s` 的二次高峰阶段，并发数提升至 `24`；`Phase 5` 为 `160-210 s` 的深度冷却阶段，并发数进一步下降至 `2`。该时间线在设计上形成了 `1x -> 8x -> 1x -> 6x -> 0.5x` 的负载变化过程，因而可以在同一轮实验中观察首次扩容、回落缩容、再次扩容和最终资源回收四类典型行为。

## 实验过程

实验过程包括四个步骤。首先，在服务器端启动 IGinX，并通过 benchmark runner 注册实验专用 UDF。随后写入固定规模的测试数据，并执行短时预热，使线程池和解释器状态进入稳定区间。之后按照五阶段时间线驱动并发负载变化，在运行过程中由客户端按秒记录吞吐和延迟，由服务端在调度周期上输出 `UDF_ADAPTIVE_METRICS` 日志。实验完成后，将客户端时间序列与服务端调度日志按时间进行对齐，得到逐秒的合并结果与汇总表，并据此绘制线程池规模、队列、CPU、吞吐和延迟的时间序列图。

这种实验流程使分析不再依赖单一结果指标。线程池是否扩缩容，可以由 `pool_size_and_active_threads.png` 直接观察；扩缩容是否由负载压力触发，可以由 `queue_and_ewma.png` 解释；外部性能结果是否随之变化，则由 `throughput_over_time.png` 与 `udf_p95_over_time.png` 给出证据。因此，实验结论建立在多类指标的交叉印证之上。

## 总体结果

从整体结果看，自适应调度池在五阶段负载下表现出完整的扩缩容过程。预热阶段线程池稳定在 `4` 个线程。主高峰开始后，线程池由 `4` 逐步扩展到 `8`、`16` 和 `32`；负载回落后，线程池从 `32` 依次收缩到 `16` 和 `8`；二次高峰到来后，线程池再次从 `8` 扩展到 `16` 和 `32`；深度冷却阶段则从 `32` 继续回落到 `16`、`8` 和 `4`。这一演化轨迹与实验设计文档中关于“高峰扩容、回落缩容、再次扩容和最终回收”的总体预期一致。

按阶段统计的结果进一步说明了这一趋势。预热阶段平均吞吐为 `8.2 queries/s`，平均 `P50` 延迟为 `490.7318 ms`，平均 `P95` 延迟为 `510.8807 ms`，线程池平均规模保持在 `4.0`。主高峰阶段平均吞吐提升至 `36.3 queries/s`，平均 `P50` 延迟为 `897.2394 ms`，平均 `P95` 延迟为 `947.7103 ms`，平均线程池规模增至 `28.6667`。回落阶段平均吞吐回到 `12.5 queries/s`，平均 `P95` 延迟下降到 `371.9880 ms`，平均线程池规模下降到 `14.2`。二次高峰阶段平均吞吐为 `27.7667 queries/s`，平均 `P95` 延迟为 `1040.9918 ms`，平均线程池规模为 `26.9333`。深度冷却阶段平均吞吐进一步回落到 `6.16 queries/s`，平均 `P95` 延迟为 `387.8573 ms`，线程池平均规模为 `14.16`，并在阶段末重新收缩到 `4`。这些统计值表明，线程池规模、吞吐和延迟均随阶段变化呈现出清晰的分段结构。

## 线程池扩缩容行为分析

如图 `pool_size_and_active_threads.png` 所示，线程池规模的变化具有明确的阶段边界。`Phase 1` 中 `poolSize` 始终保持在 `4`，与初始配置一致。进入 `Phase 2` 后，`t=31 s` 时线程池已扩展到 `8`，`t=36 s` 时扩展到 `16`，`t=41 s` 时扩展到 `32`。这说明在主高峰开始后的约 `10 s` 内，系统完成了从基线配置到峰值线程规模的调整过程。考虑到调度周期为 `2 s`，冷却时间为 `5 s`，这一响应速度处于工程上可接受的范围内。

回落阶段的缩容过程同样清晰。`Phase 3` 开始时，线程池仍保持在高峰阶段留下的 `32` 个线程，`t=96 s` 时收缩到 `16`，`t=112 s` 时继续收缩到 `8`。此后在 `4` 并发负载下维持稳定，表明调度器并未长期维持过高线程数。进入 `Phase 5` 后，线程池再次完成进一步收缩：`t=170 s` 时下降到 `16`，`t=186 s` 时下降到 `8`，`t=202 s` 时最终回到 `4`。由于 `Phase 5` 的目标并发仅为 `2`，此时线程池能够继续回收到最小线程数，说明其具备在低负载阶段释放资源的能力。

图中 `activeThreads` 与 `poolSize` 的配合也为结果解释提供了帮助。在高峰阶段，`activeThreads` 在扩容完成后能够接近峰值线程规模，说明新增线程承担了实际工作。回落与冷却阶段 `activeThreads` 明显下降，随后才出现 `poolSize` 的收缩，这与“先出现空闲，随后逐步缩容”的设计逻辑是一致的。

## 队列压力与扩容触发分析

如图 `queue_and_ewma.png` 所示，主高峰阶段的排队信号出现在扩容之前。`Phase 2` 开始后的第一个采样点 `t=31 s`，`queueLength` 已达到 `24`，同时线程池开始从 `4` 扩展到 `8`。在接下来的若干秒内，队列长度仍处于较高水平，线程池继续扩容到 `16` 和 `32`。这一过程与实验假设 H1 保持一致，即队列积压先出现，调度器随后在若干调度周期内触发扩容。值得注意的是，随着线程池规模逐步提升，队列长度和 `queueEwma` 很快回落到接近零的水平，说明扩容动作对队列积压具有实际缓解作用。

二次高峰阶段同样可以观察到相似过程。`Phase 4` 开始后的 `t=132 s`，队列长度上升到 `10`；`t=134 s` 线程池扩展到 `16`，同时 `queueLength` 进一步达到 `12`；`t=139 s` 线程池扩展到 `32` 后，队列长度重新下降。这表明调度器能够在经历一次完整扩缩容后再次根据排队信号完成扩容，因果顺序仍然清晰。与主高峰相比，二次高峰的队列峰值较低，说明调度器和运行环境在前一阶段完成激活后，系统在第二次高峰中能够更快进入收敛状态。不过，从完整扩容到最大线程规模所需的时间看，两次高峰处于同一数量级，本文据此认为“再次快速扩容”得到支持，但证据尚不足以说明二次高峰的响应速度显著优于首次高峰。

## CPU 指标与调度决策关系分析

如图 `cpu_and_ewma.png` 所示，CPU 使用率在高峰阶段有所抬升，且与线程池扩容和高吞吐区间存在对应关系。主高峰阶段的平均 `cpuUsage` 为 `0.0772`，高于预热阶段的 `0.0188`；二次高峰阶段平均 `cpuUsage` 为 `0.0598`，同样高于回落和冷却阶段。全程 CPU 峰值出现在 `Phase 2` 的 `t=68 s`，对应值为 `0.1095`。这说明自由线程环境下，随着并发和线程池规模的提升，系统确实出现了更高的计算活跃度。

另一方面，本轮实验中的 CPU 使用率整体低于配置中的高水位阈值 `0.85`。因此，从观测结果看，CPU 高水位限制并未成为本轮扩容过程中的主要约束项。扩容的主要触发信号仍然来自队列积压及其 EWMA 变化，CPU 指标在本实验中主要起到辅助解释作用。这一现象与实验设计文档中对 `cpuUsage` 和 `S_cpu` 的定位一致，即其作用在于解释扩容抑制与缩容条件，而不要求其在每一轮实验中都成为主导因素。

## 吞吐结果分析

如图 `throughput_over_time.png` 所示，吞吐随阶段变化呈现出明显的分段特征。预热阶段平均吞吐为 `8.2 queries/s`，与 `4` 并发负载相匹配。进入主高峰阶段后，平均吞吐提升到 `36.3 queries/s`，并在 `t=43 s` 达到全程最大值 `64.0 queries/s`。这一结果说明，线程池扩容后系统能够在自由线程环境下承载明显更高的请求完成速率。

回落阶段的平均吞吐下降至 `12.5 queries/s`，深度冷却阶段进一步下降到 `6.16 queries/s`，变化方向与目标并发设置一致。二次高峰阶段平均吞吐为 `27.7667 queries/s`，显著高于回落阶段和冷却阶段，但低于主高峰阶段。这一差异主要与二次高峰的目标并发为 `24`、低于主高峰 `32` 有关，因此其吞吐水平低于主高峰是符合负载设计的结果。总体上，吞吐图与线程池规模图之间存在稳定对应关系，即更高的并发和更大的线程池规模对应更高的完成请求速率。

需要说明的是，`throughputPerSecond` 在该 benchmark runner 中定义为每秒完成请求数，因此图中值反映的是每秒 drain 出来的完成请求条数。该指标能够直观反映系统外部处理能力，但并不能单独区分性能变化究竟来自调度决策、运行时并发能力，还是 UDF 本身的计算特征。因此，对吞吐结果的解释应与队列和延迟图联合进行。

## 延迟结果分析

如图 `udf_p95_over_time.png` 所示，延迟变化与负载阶段切换保持高度一致。预热阶段 `P50` 和 `P95` 基本稳定在 `400-600 ms` 区间。进入主高峰后，两条曲线同步抬升，在 `t=37 s` 处 `P95` 达到全程最大值 `1521.2214 ms`，随后随着线程池扩容完成而回落，并在主高峰后半段稳定在约 `800-950 ms` 区间。这一过程说明，高峰初期的尾延迟抬升与队列积压同时出现，随后随着线程池扩容和队列消退而缓解。

回落阶段延迟迅速下降。`Phase 3` 中平均 `P95` 为 `371.9880 ms`，接近甚至低于预热阶段水平，说明在负载降低且线程池逐步缩容的同时，系统可以重新回到较低延迟区间。二次高峰阶段延迟再次升高，平均 `P95` 为 `1040.9918 ms`，峰值为 `1292.8007 ms`。这一数值低于主高峰初期出现的 `1521.2214 ms` 峰值，说明在经历一次完整扩缩容后，系统在第二次高峰中虽然仍然承受显著压力，但尾延迟未进一步恶化。结合队列峰值和线程池扩容过程，可以认为调度器在二次高峰中的响应保持有效。

值得注意的是，本轮实验中 `P50` 与 `P95` 大多同步变化，二者之间的间距在高峰初期略有扩大，在收敛后重新缩小。这表明高峰阶段延迟上升并非只集中在极少数慢请求上，系统整体请求完成时间都受到了负载变化影响；与此同时，`P95` 峰值对排队和扩容滞后的反应仍然更敏感，因此其更适合作为观察调度有效性的尾部指标。

## 综合图表分析

总览图 `adaptive_behavior_overview.png` 将线程池规模、队列、CPU、吞吐和延迟五类指标放置在同一时间轴上，能够更完整地展示这一轮实验的因果链条。其一，在 `Phase 2` 和 `Phase 4` 的起始位置，可以先观察到目标并发上升，随后队列长度增长，再之后线程池规模扩大。其二，在扩容完成后，吞吐上升，延迟从峰值区间回落到相对稳定区间。其三，在 `Phase 3` 和 `Phase 5`，目标并发下降后，队列迅速消失，活跃线程数下降，线程池规模在若干调度周期后逐步回收。各类指标之间不存在明显冲突，这说明实验结果具备较好的整体一致性。

从图形形态看，线程池规模的变化为少量阶梯跳变，未出现高频来回摆动；`queueEwma` 和 `cpuEwma` 的变化较平滑，与原始瞬时指标方向一致；吞吐和延迟曲线在阶段边界处存在明显折点，与目标并发变化时间基本对齐。这些现象共同表明，调度器的工作过程具有可解释的阶段性和收敛性，没有出现明显失稳。

## 对实验假设的验证

对于 H1，即“高峰阶段队列先上升，调度器随后扩容”，本轮实验给出了明确支持。主高峰开始时 `queueLength` 在 `t=31 s` 达到 `24`，同时线程池从 `4` 扩展到 `8`，随后进一步扩展到 `16` 和 `32`；二次高峰阶段也观察到相同顺序。对于 H2，即“扩容完成后线程池应收敛到稳定区间而非频繁抖动”，图中主高峰和二次高峰后半段的 `poolSize` 都维持在稳定平台，说明该假设得到支持。

对于 H3，即“负载回落后线程池应逐步回落到接近基线所需水平”，实验结果同样提供了支持。`Phase 3` 中线程池从 `32` 收缩到 `16` 再到 `8`，`Phase 5` 中继续从 `32` 收缩到 `16`、`8` 和 `4`，最终回到最小线程数。由于回落和冷却阶段均仍有持续请求存在，因此这一结果说明缩容逻辑可以在低负载下渐进回收多余资源，并不要求系统进入完全空闲状态。

对于 H4，即“经历一次完整扩缩容后，二次高峰应能够再次快速扩容，并且不出现明显振荡”，实验结果给出了部分支持。二次高峰中线程池确实再次从 `8` 扩展到 `16` 和 `32`，且未观察到明显振荡。就响应速度而言，二次高峰从首次排队到扩展到 `32` 的过程与首次高峰处于相近时间尺度，说明系统具备再次扩容能力，并保持了良好的稳定性。关于“显著快于首次冷启动”这一更强结论，本轮数据只能给出有限支持，因此本文不对该点作更强推断。

## 功能有效性的证据链条

本实验之所以能够用于验证自适应调度功能，原因在于其提供了从负载变化到调度决策，再到外部性能结果的完整证据链。首先，目标并发按照预设时间线发生离散变化，为调度器提供了明确的外部刺激。其次，`queueLength` 与 `queueEwma` 在高峰阶段出现可观测抬升，说明系统确实形成了待处理压力。再次，`poolSize` 在若干调度周期内随之扩大，并在低负载阶段逐步回收，说明调度器在执行扩缩容动作。最后，吞吐和延迟与这一过程同步变化，表明这些调度动作会影响用户可见的执行结果。

如果缺少其中任意一环，实验都难以支撑对功能有效性的判断。仅观察吞吐提升，无法证明提升来自调度器；仅观察线程池规模变化，无法说明这些变化对请求处理是否有意义；仅观察队列长度，则无法确认系统是否真正做出响应。本实验同时采集并对齐了内部状态和外部结果，因此可以较为充分地说明：在自由线程 Python 环境下，IGinX 自适应 Python UDF 调度池能够根据动态负载变化完成扩容与缩容，并在整体上符合设计文档中的行为预期。

## 结果边界与讨论

需要指出的是，本文结论的重点是“调度行为是否符合设计预期”，并非对所有性能收益来源作因果归因。自由线程 Python 运行时、NumPy 计算特征、服务器资源条件以及 UDF 实现细节都会影响吞吐和延迟的绝对数值。因此，本文更重视时间序列中的结构性现象，包括扩容是否在排队后出现、缩容是否在负载回落后出现，以及这些变化是否与吞吐和延迟变化保持一致。

在这一边界下，本轮实验结果已经能够支持论文中的核心论断：自适应 Python UDF 调度池在动态五阶段负载下具备可观测、可解释且相对稳定的扩缩容能力；其行为与队列长度、EWMA 指标、吞吐和查询延迟之间存在一致的时间对应关系；因此，该调度机制能够满足工程设计中关于动态资源调节的基本功能要求。
