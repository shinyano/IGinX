# IGinX 自适应 Python UDF 调度池动态扩缩容行为观测实验设计

## 1. 文档目的

本文档用于说明 IGinX 中自适应 Python UDF 调度线程池的动态扩缩容行为观测实验设计。本文档服务于硕士论文中的工程设计实验评估部分，重点回答如下问题：

- 在时间变化的负载模式下，自适应调度器是否能够按预期触发扩容与缩容。
- 调度器的扩缩容决策是否与任务队列长度、CPU 利用率、EWMA 平滑指标和查询延迟变化保持一致。
- 系统在经历一次完整扩缩容后，是否能够在二次高峰中继续快速响应，同时避免明显过冲与振荡。

本实验不再以存在正确性风险的旧版解释器队列机制作为性能对照组，而是聚焦于当前自适应调度池本身的运行行为与工程有效性。

## 2. 实验背景

### 2.1 系统背景

IGinX 在 Python UDF 执行路径中引入了自适应 UDF 专用线程池，其设计目标包括：

- 将 Python UDF 从通用内存任务线程池中剥离，实现物理隔离。
- 根据队列长度、活跃线程比例和 CPU 利用率动态扩缩线程池。
- 在线程退出时回收线程本地 Python 解释器，避免资源泄漏。
- 在负载回落时自动回收闲置线程，降低资源占用。

设计细节可参考：

- `core/src/main/java/cn/edu/tsinghua/iginx/engine/physical/udf/DESIGN.md`

### 2.2 为什么不再做旧架构性能对比

PR #454 之前的旧版 Python UDF 执行方案采用固定解释器队列，并允许解释器实例在不同工作线程之间迁移使用。[PR #454](https://github.com/IGinX-THU/IGinX/pull/454/changes) 之后，系统演进为“解释器与执行线程绑定”的实现方式。

进一步分析和复现实验表明，旧方案不仅存在固定容量上限问题，还在高并发场景下暴露出运行时正确性风险。因此，后续实验不再以“旧架构 vs 新架构”作为主问题，而是转向评估当前自适应调度池本身是否按照设计预期工作。

## 3. 实验目标

本实验的总体目标是验证自适应 UDF 调度线程池在动态变化负载下的扩缩容行为是否符合设计预期，并量化其与关键运行指标之间的对应关系。

具体子目标如下：

1. 观察调度器在负载突增阶段是否能够及时扩容。
2. 观察调度器在负载回落阶段是否能够渐进式缩容。
3. 观察扩缩容过程中是否存在明显过冲、滞后或振荡。
4. 观察二次高峰阶段调度器是否能够再次快速扩容。
5. 为论文中的“自适应调度有效性”提供可视化、可解释的时间序列证据。

## 4. 研究问题与假设

### 4.1 研究问题

#### RQ1

在动态阶梯式负载下，自适应调度器是否能够在任务队列积压出现后若干调度周期内触发明显扩容。

#### RQ2

在负载回落后，自适应调度器是否能够在冷却窗口与空闲判定条件满足后逐步缩容，而不是长期维持高线程数。

#### RQ3

在经历一次完整扩缩容后，调度器是否能够在二次高峰中再次快速扩容，并保持稳定而不过冲。

#### RQ4

查询延迟、队列长度、CPU 利用率和 EWMA 指标的变化是否能够与扩缩容决策形成一致的因果链条。

### 4.2 实验假设

#### H1

在高峰阶段，任务队列长度将先于线程池规模上升；调度器在观测到持续积压后将逐步扩容，而不是无限期维持初始线程数。

#### H2

在高峰阶段的扩容完成后，线程池规模应在冷却期约束下收敛到某个稳定区间，而不是在相邻调度周期中频繁反复调整。

#### H3

在负载回落阶段，若队列压力消失且 CPU 利用率下降，线程池规模应逐步回落至接近基线负载所需的水平。

#### H4

在二次高峰阶段，由于线程池与解释器环境已经历首次激活，调度器的再次扩容响应应快于首次冷启动阶段，且不应出现明显振荡。

## 6. 工作负载设计

### 6.1 UDF 负载

UDF 负载默认采用 `DataFrame -> NumPy` 的向量化计算 workload，对输入数据反复执行平方与求和操作。其特征为：

- 输入接口仍然是 `DataFrame`
- 计算主要依赖 `NumPy` 的底层 native 实现
- 更贴近 IGinX Python UDF 的实际使用预期
- 在自由线程 Python 运行时下，更容易体现线程并发执行带来的收益，并放大调度池扩缩容的观测信号

### 6.2 动态负载阶段设计

本实验采用五阶段阶梯式负载曲线，对调度器施加“预热 -> 首次高峰 -> 回落 -> 二次高峰 -> 深度冷却”的时间变化压力。

建议的优化版时间线如下：

- **Phase 1 (0-30s)**：预热期，`4` 并发，与线程池初始线程数保持一致
- **Phase 2 (30-90s)**：主高峰期，升至 `32` 并发，约为初始线程数的 `8x`
- **Phase 3 (90-130s)**：回落稳定期，降回 `4` 并发
- **Phase 4 (130-160s)**：二次高峰期，升至 `24` 并发，约为初始线程数的 `6x`
- **Phase 5 (160-210s)**：深度冷却期，降至 `2` 并发

若受实验时长限制，也可退化为原始 `180s` 时间线，但论文主实验推荐使用 `210s` 版本，以保证收敛过程更清晰可观测。

### 6.3 参数设计依据

- 并发水平按初始线程数 `4` 的相对倍数设计，形成 `1x -> 8x -> 1x -> 6x -> 0.5x` 的阶梯式负载，便于从图上直接对应预热、首次扩容、回落缩容、再次扩容和最终回收五类行为。
- 高峰值 `32` 并发显著高于初始容量，更容易在短时间内形成可观测的队列积压，使扩容触发条件与 `P95` 延迟变化更清晰。
- 回落阶段不直接降为 `0`，而是先回到 `4` 并发，用于验证系统是否能够在仍有持续请求的情况下回收多余线程，而非仅在完全空闲时才缩容。
- 第二次高峰选择 `24` 并发而非重复 `32` 并发，用于模拟业务回潮场景，并观察调度器在经历一次完整扩缩容后能否快速再次扩容且避免明显过冲。
- 各阶段持续时间均显著长于 `2s` 基础调度周期、`5s` 冷却期以及连续若干周期的空闲判定窗口，从而保证各阶段内能够观察到完整的状态收敛过程，而不是仅记录瞬态扰动。

## 7. 实验变量设计

### 7.1 自变量

#### 时间阶段 `phase`

取值：

- `phase1_warmup`
- `phase2_peak`
- `phase3_recovery`
- `phase4_rebound`
- `phase5_cooldown`

#### 时间相关并发 `concurrency(t)`

该变量由时间线决定：

- `0-30s`: `4`
- `30-90s`: `32`
- `90-130s`: `4`
- `130-160s`: `24`
- `160-210s`: `2`

### 7.2 因变量

建议按秒采样以下指标：

- 当前线程池核心线程数 `poolSize`
- 当前活跃线程数 `activeThreads`
- 任务队列长度 `queueLength`
- CPU 利用率 `cpuUsage`
- EWMA 平滑队列指标 `S_queue`
- EWMA 平滑 CPU 指标 `S_cpu`
- 每秒 UDF 吞吐量 `throughputPerSecond`
- UDF 查询 `P95` 延迟

其中：

- `poolSize` 用于观测扩容与缩容是否发生
- `activeThreads` 用于区分“线程已创建”与“线程确实在忙”
- `queueLength` 和 `S_queue` 用于解释扩容触发原因
- `cpuUsage` 和 `S_cpu` 用于解释扩容抑制与缩容条件
- `P95` 用于衡量用户视角的查询质量变化

### 7.3 控制变量

为保证实验可比性，固定以下参数：

- 数据规模：`rows=10000`
- 列数：`cols=10`
- 每次 UDF 调用内部计算轮数：`loops=20`
- 自由线程 Python 运行环境
- IGinX 代码版本
- 服务器硬件与部署方式
- 自适应线程池参数：
  - `udfPoolInitialThreads=4`
  - `udfPoolMinThreads=4`
  - `udfPoolMaxThreads`
  - `udfPoolExpandThreshold`
  - `udfPoolShrinkThreshold`
  - `udfPoolCpuHighThreshold`
  - `udfPoolCpuLowThreshold`
  - `udfPoolScheduleIntervalMs=2000`
  - `udfPoolCooldownMs=5000`

## 8. 实验流程设计

### 8.1 运行前准备

1. 在本机完成 `core` 模块编译与 assembly 打包。
2. 将发行包上传到服务器。
3. 在服务器准备好自由线程 Python 环境及依赖。
4. 确认底层存储、ZooKeeper、IGinX 运行依赖可用。

### 8.2 配置实验点

服务器脚本在运行本实验时应固定以下配置：

1. 设置 `pythonCMD`
2. 启用自适应 UDF 池：
   - `udfPoolEnabled=true`
   - `pythonUdfLegacyExecutionEnabled=false`
3. 设置自适应参数：
   - `udfPoolInitialThreads=4`
   - `udfPoolMinThreads=4`
   - `udfPoolMaxThreads=CPU*2` 或预设值
   - `udfPoolScheduleIntervalMs=2000`
   - `udfPoolCooldownMs=5000`

### 8.3 执行动载实验

1. 启动 IGinX
2. 注册 benchmark UDF
3. 写入固定测试数据
4. 执行短时预热，确保解释器和线程池进入稳定状态
5. 按预设五阶段时间线驱动并发负载
6. 在每个调度周期记录调度器决策日志
7. 按秒记录线程池、队列、CPU、吞吐和延迟指标

### 8.4 清理与重复

1. 停止 IGinX
2. 清理残留端口
3. 重复多轮实验以确认趋势一致性
4. 恢复原始配置

## 11. 结果分析建议

### 11.1 预期现象

若设计成立，预期会观察到：

1. `Phase 2` 开始后，队列长度先上升，随后线程池在若干调度周期内发生明显扩容。
2. 扩容后线程池规模在高峰段稳定于合理区间，而不是连续过冲。
3. `Phase 3` 回落后，系统在满足空闲判定后逐步缩容，并回到接近基线负载所需的线程规模。
4. `Phase 4` 二次高峰时，系统能够再次快速扩容，且响应速度优于首次冷启动阶段。
5. `Phase 5` 深度冷却阶段，线程池继续回收闲置资源，整体过程中不应出现明显的高频振荡。

### 11.2 如何解释扩容滞后

如果 `Phase 2` 中没有迅速扩容，应优先从以下角度分析：

- 队列积压是否持续时间不足
- EWMA 平滑是否导致触发信号被延后
- CPU 抑制阈值是否过于保守
- 冷却时间是否过长
- 负载是否实际上没有形成足够的排队压力

### 11.3 如何解释缩容滞后

如果 `Phase 3` 或 `Phase 5` 中缩容不明显，应优先从以下角度分析：

- 空闲判定窗口是否过长
- 队列是否存在残余积压
- CPU 利用率是否仍高于低水位
- 活跃线程是否迟迟无法归零

### 11.4 如何解释二次高峰的响应行为

若 `Phase 4` 的扩容明显快于首次高峰，可解释为：

- 线程池与解释器环境已完成首次激活
- 再次扩容时冷启动成本降低

若 `Phase 4` 出现明显过冲，则需考虑：

- 冷却窗口不足
- EWMA 权重过于激进
- 队列阈值设置偏低

## 12. 有效性与威胁分析

### 12.1 内部有效性

潜在威胁包括：

- 压测线程本身实现存在偏差
- 调度日志与秒级采样时间对不齐
- 失败样本未被正确过滤
- 会话池或客户端线程池先成为瓶颈

缓解方式包括：

- 固定压测参数与服务器环境
- 每轮实验前重启 IGinX
- 输出调度周期日志和秒级采样结果
- 使用多轮重复观测确认趋势一致

### 12.2 构造有效性

本实验测量的是：

- 自适应调度器在动态负载下的行为是否符合设计预期

而不是：

- 不同历史实现之间的端到端性能对比
- Python 函数本身的微基准性能

### 12.3 外部有效性

本实验主要适用于：

- CPU 密集型 Python UDF
- 存在明显高峰、回落和二次回潮特征的业务负载

对以下场景仍需进一步实验：

- I/O 密集型 UDF
- 长尾模型推理型 UDF
- 大规模 NumPy / pandas 主导型 UDF

## 14. 关于自由线程 Python 的实验口径

本实验建议采用：

- 自由线程 Python 运行时
- `pandas` / `numpy` 风格的 `DataFrame` UDF 负载

原因如下：

1. 更符合当前 IGinX Python UDF 的实际接口与使用方式。
2. 根据远程实验观察，自由线程 Python 比标准 GIL Python 更容易体现该场景下的并发收益，实验现象更清晰。
3. 更有利于观察调度池扩缩容对吞吐、排队和延迟的影响。
4. 仍然能够把论文主线聚焦在“调度策略与资源管理机制”的工程验证上。

若后续需要与标准 GIL Python 做对照，建议另设补充对比实验；本实验主线默认采用自由线程 Python。
